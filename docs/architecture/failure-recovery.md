# 失败恢复

从 v1.0.1 起，支持在失败后接续原任务。失败任务首次打开默认显示日志，也可检查变更与失败原因；详情页签按任务保存。安装包见 [v1.0.1 Release](https://github.com/zhoujiacheng1031/Model-Foreman/releases/tag/v1.0.1)。

## 使用与行为

失败任务详情和运行记录提供「从失败处继续」与「重新创建任务」。前者先展示失败原因、可复用步骤和恢复条件，启动时再次检查现场；后者沿用旧行为，创建新的运行与隔离工作区并保留原记录。

对于使用步骤 worktree 的并行执行流程：

| 步骤状态 | 恢复动作 |
| --- | --- |
| 已汇总 | 校验产出提交仍属于任务分支，复用结果 |
| 已封存、待汇总 | 校验工作区与封存提交，汇总已有结果 |
| 失败或被同批失败中断 | 沿用原工作区与过程记录，增加尝试次数后接续 |
| 尚未执行 | 依赖汇总完成后执行 |

默认串行流程与审查后的主执行角色返工仍以阶段为检查点，沿用原工作区中的改动，不提供每一步独立复用。验证或审查阶段失败时，保留实现报告，重新运行完整验证与独立审查。实现阶段失败时清除旧实现、验证和审查产物，再生成新的报告。失败的验证始终阻止交付；跳过验证仍显示为 skipped。

累计用量、资源记录、任务 ID、分支和原失败日志保留。Agent 资源记录包含步骤 ID、Agent ID 和真实尝试次数。每次失败重新保存现场；恢复日志记录本次复用与待汇总数量。这里恢复的是 Foreman 管理的文件、提交和过程记录，不是 CLI 的私有会话。

长期目标在未耗尽预算和子任务尝试次数时优先接续有有效检查点的失败任务，并累计一次尝试与目标循环。条件不满足时沿用原有重新创建子任务的路径。普通任务恢复入口拒绝直接启动目标所属任务，避免绕过目标调度约束。

## 恢复前检查

失败时将以下现场保存到 SQLite 的 runs.failure：阶段、时间、错误、原项目 HEAD、合同摘要，以及任务工作区和未汇总 Agent 工作区的 HEAD 与内容指纹。指纹包含已跟踪文件差异、暂存差异及未跟踪文件内容；符号链接记录链接目标。

恢复要求：

- 原任务尚未交付或丢弃，存在完整的已批准合同和失败检查点。
- 原项目 HEAD 仍是任务基线；合同、任务工作区和未汇总步骤的现场未改变。
- worktree 仍登记在原仓库，使用原分支，基准提交仍为祖先，且没有未解决的合并冲突。
- 步骤与合同的范围、依赖一致；待复用报告没有未解决事项，已汇总提交仍在任务分支历史中。

现场缺失或已变化时，展示原因并拒绝接续，保留原文件与记录。旧版本任务没有失败检查点时可以重新创建。当前版本采用保守拒绝策略，尚不自动吸收失败后的人工编辑、重建缺失 worktree 或解决汇总冲突。

恢复启动使用 SQLite 条件更新，在同一次写入中核对失败检查点、切换阶段并失效旧验证与审查结论。过期请求和重复请求不能清除现有证据或再次启动；应用在 queued 阶段退出时保留原恢复阶段。

worktree 不构成操作系统安全沙箱。外部数据库、网络请求等副作用不在文件指纹范围内；接续提示要求先核实不确定操作的结果，不能将文件检查点视为外部操作恰好执行一次的保证。

## 验收

`npm test` 使用真实临时 Git 仓库与 SQLite、受控执行器注入故障，覆盖重启接续、同批成功产出、原始故障保留、文件和分支变化、过期恢复请求、重复启动、重新验证、失败门禁与目标尝试次数。

另提供显式启用的真实 CLI 验收；需事先安装并登录相应 CLI，填写账户可用模型，调用会消耗真实额度：

```bash
npm run test:harness -- codex <model>
npm run test:harness -- claude <model>
npm run test:harness -- zcode native-default
```

该验收在临时仓库中让实际 CLI 完成两个独立步骤，在第三步模型调用前注入连接失败，重新打开 SQLite 后接续第三步，最后运行本地命令与实际模型审查，断言前两步未重复调用。默认测试跳过该验收，跳过不代表通过。真实断网、CLI 进程终止、混合执行器和 Windows 需要分别验证，不能由此场景推定。

真实验收现包含两个场景：调用前故障，以及第三步 CLI 输出首个事件后实际终止其进程再恢复。可分别用 `npm run test:harness -- codex <model> -t before-call` 和 `npm run test:harness -- codex <model> -t process-termination` 选择；运行命令不带筛选时执行两个场景。进程终止场景只有在实际 CLI 被终止并返回失败后，才进入数据库重开和恢复断言。

实际崩溃注入在 POSIX 上使用 SIGKILL 终止该次执行独立进程组，Windows 使用进程树终止接口；它与用户主动暂停的温和取消分开验证。用户主动取消时，即使 CLI 的 SIGTERM 处理器返回退出码 0，Foreman 仍将该调用判为取消，避免把中断输出当作成功。并行成员针对同一模型与推理强度的并发预检会合并为一次实际探测；配置失效操作不会被尚未结束的旧探测重新写回缓存。

为跨限流窗口或验收宿主重启接续，可指定稳定的结果目录：

```bash
FOREMAN_HARNESS_REPORT_DIR=/absolute/path/to/results npm run test:harness -- codex <model>
```

每个场景保存 JSON 进度记录、运行 ID、临时仓库与 SQLite 路径、模型调用时间、限流等待时间及源码哈希。临时现场在未完成时保留；再次使用同一目录会打开原任务。测试不会将限流暂停当作通过，而是按执行器给出的等待时间接续原阶段，每个场景保留最多 55 分钟等待上限。完成条件还包括真实本地验证、真实模型审查、临时源仓库合并，以及合并后文件内容校验；完成结果记录提交与文件哈希。

### 已验证范围

2026-11-23 至 24 日，在 macOS 临时仓库中分别使用 Codex CLI 0.162.1 / gpt-6.1-sol 和产品 ZCode 执行器 / 原生模型 glm-5.3，完成调用前失败和进程终止后的恢复。核对了原任务 ID、已完成步骤复用、实际模型审查、独立本地验证、临时源仓库合并及文件字节与哈希。

ZCode 产品执行器实测中，两项恢复场景的 A/B/C 尝试次数均为 1/1/2，另完成规划合同及只读工作区检查。限流与权限失败记录保留在本地验收材料中；这些失败不计为通过。

v1.0.1 发布时另执行源码回归、生产构建与双端包内校验；具体记录随 Release 附件提供。Windows 安装包构建和内容校验不代表 Windows 上的真实 CLI 恢复已通过。Claude、Windows、真实断网和混合执行器的真实模型恢复尚未完成本轮验收。
